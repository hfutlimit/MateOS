## 0. 一句话结论

你已经把"正确的难点"都解决了：Terminal CAS、envelope 幂等、Redis 原子 slot、消息流 projection、single source of truth——这些是多数团队上线半年后才会还的债，你在设计期就还了。

但**你在为一个 10 人团队 + 已验证的产品写架构，而 MateOS 现在是单人项目、零代码、零用户**。证据：

- PRD §1.1 明确写"V1 只证明一件事：人和 Agent 能像团队一样协作"，Non Goals 明确禁止"无人类参与的 Agent 间循环"
- 实际设计已有 **~30 张表**（E1–E10）+ **8 张新表**（autonomous-delivery）+ Scheduler 自治等级 + DAG replanning + OPEN_CLAIM 抢单
- README 说 M1–M6，SYSTEM_DESIGN 说 M1–M9 + V1+

**核心建议：先做减法再写第一行代码。** 下面按严重度排。

## 2. 架构问题（按严重度）

### P0-1 「一件事」有 6 个容器 —— 最大风险

| 概念 | 归属 | 是什么 | 问题 |
| --- | --- | --- | --- |
| Mission | Delivery 新域 | PO 选多 Story 形成的交付目标 | 与 WorkItem 的 EPIC 类型重叠 |
| WorkItem | E8 | PO/Provider 视角的 Story/Task/Bug | 与 WorkUnit 只差"谁在看" |
| WorkUnit | Delivery 新域 | Agent 内部交付单位，optional promote 为 WorkItem | **optional promote = 用户可以不知道自己有几个"事"** |
| Topic | E3 扩展 | Channel 内消息聚类 | 原型 P5b 已给它 5 个状态，实际在做 WorkItem 的活 |
| CollaborationRequest | E4 | 一次协作请求 | 用户视角它才是"我 @ 了一下" |
| Execution | E7 | 一次执行 | 用户不关心，但 UI 要展示进度 |

**后果**：MVP 内 E8 §8 把 `WorkItem → Trigger` 推到 V1+，等于 **WorkItem 与 Execution 互不可见**——你要证明的"人和 Agent 一起推进工作"在 MVP 里是断的。

**建议**：
1. 定一个**用户可感知的"事"= WorkItem**，其余全部降级为内部实现。
2. WorkUnit **不要 optional promote**——要么它就是 WorkItem 的一种（加 `source: HUMAN | AGENT_PLANNED`），要么它永不对外。
3. Topic 不承载状态（04 文档 §2.1 已经这么写了，但 P5b 原型违反，改原型）。
4. 引入 **Work Thread 投影**（只读，不是新事实源）：以 `work_item_id` 为聚合键，把 collaboration_requests + decision_records + executions + memory_proposals 投影成一条时间线。**领域模型保持纯净，UI 只消费投影**。

**建议**：
1. 抽 `docs/spec/invariants.md` 作为**不变量单一事实源**：6 态、Decision 态、Permission 态、Provider 路由规则、协议幂等键、slot 语义。其他文档只引用，不复制。
2. 把状态机/枚举落成 `packages/contracts` 的 TS 常量 + zod schema，文档从代码生成或 CI 校验。
3. CI 加禁用词扫描：`AgentBoard` / `can_execute` / `can_review` / `REQUEST` / `active_slots` / `work_item_projections`。
4. 版本号只保留 PRD / SYSTEM_DESIGN / UI DS 三个顶层号，子文档用日期。现在有 v0.4 / v0.3.2 / v0.6 / v0.4.2 / v0.4.3 / v0.1 六套并行。

### P0-3 Autonomous Delivery 与 V1 突破点冲突

`docs/design/detailed/autonomous-delivery/` 是一整套**自主交付子架构**：Mission Grill、Requirement Brief、WorkUnit DAG、Dynamic Replanning、Scheduler Autonomy Level 0–3、OPEN_CLAIM 抢单、Handoff 协议。新增 8 张表。

这与 PRD §1.1「V1 只证明一件事」和 Non Goals「禁止无人参与 Agent 循环」**直接矛盾**。它本身设计得很认真（00-integration-map 的 9 条 Invariant 写得很好），但出现在 M1 之前就是债务。

**建议**：整个目录移到 `docs/design/future/`，标注"V2 愿景设计，不作为 M1–M9 依据"。保留它，但别让它污染当前实施路径。真要留一部分，只留 **Topic + Needs You**（因为它解决的是 UX 真问题，见 §4 U1）。

### P1-1 Redis slot 是事实源，但没有重建路径

per-lease ZSET + renew 是对的（比 EXPIRE 整个 key 好）。但 `used` 只存在于 Redis：Redis 重启 /  failover / key 丢失 → 计数错 → 要么超发、要么永久死锁。文档里没有 reconciler。

**建议**：
1. 明确 `used` 是"可从 DB 重建的缓存"，不是权威值。
2. 启动时 rebuild：从 `agent_executions.status IN (PENDING, RUNNING)` + `collaboration_requests.status='PENDING'` 重建。
3. 周期对账 job + 孤儿 lease 回收（现在崩溃要等 600s TTL）。
4. `lease TTL` 必须 > `renew 周期 × 3`，且独立于 `deadline_s`（现在两者都是 600，长任务会误过期）。

### P1-2 Permission：为 1 个真实生效的键建了整套设施

7 键里 `execute_code` 全 DENY、`create_pr` Agent DENY、其余全 ALLOW —— **MVP 实际只有 `write_memory` 一条走 REQUIRE_APPROVAL**。为它建了三层覆盖 + Redis 缓存 + pub/sub 失效 + 7×3 矩阵表。

更根本的：`REQUIRE_APPROVAL` 是**流程指令**，不是**权限结论**。它混进三态 check 导致：Guard 返 403 但语义是"可申请"、E6 §5.2 与 §10 自相矛盾、E5 里找不到 `policy.evaluate()` 调用点。三个症状一个病根。

**建议**：
1. `check()` 返回 `{ effect, approval_route }`，把"去哪儿批"显式化。
2. `scope_type` 补 `ORG` / `TEAM`——否则 owner 权限只能靠代码 `if (isOwner)` 特判，又一个双事实源。
3. MVP 可以先把矩阵硬编码成常量，配置化推迟到真有多个可配权限时。
4. E5 §5.1 补上 `policy.evaluate('write_memory')` 的调用点，否则门禁形同虚设。

### P1-3 选型的两处硬冲突

| 冲突 | 说明 | 建议 |
| --- | --- | --- |
| **antd 6 vs 自建 tokens.css** | 两套设计体系并存，前端必然重写一遍组件 | 二选一：用 antd ConfigProvider 把 tokens.css 映射进去，或明确 headless 路线（Radix + Tailwind）。**别两套都留** |
| **Prisma vs PG 分区** | Prisma migrate 管不了声明式分区，会反复想删；且 E3 的 `PARTITION BY RANGE(created_at)` 配 PK `(channel_id, seq)` **在 PG 里建不出来**（分区表唯一约束必须含分区键） | MVP 不分区，用 `(channel_id, seq)` 索引 + 按月归档 job |
| **运维面过重** | PG + Redis + BullMQ + MinIO + pgvector + OTel + Prometheus + Grafana + Loki，单人 | 先结构化日志 + `/metrics` + 本地磁盘 artifact；OTel 全家桶等有用户再说 |

### P1-4 实施顺序：从横切改竖切

现在是 M1 身份 → M2 消息 → M3 Agent → M4 协作 → M5 记忆 → M6 WorkItem → M7 权限 → M8 执行 → M9 可观测。**九个里程碑里前六个都无法演示产品价值。**

建议拆成 3 条 vertical slice，每条端到端可演示：

| Slice | 打通什么 | 涉及 Epic |
| --- | --- | --- |
| **S1 一句话到产出** | @mention → resolver → decision → execution → 输出回帖 | E1 + E2 + E3 + E4 + E7 最小面 |
| **S2 记忆与闸门** | memory proposal → 审批 → Source 溯源 + Inbox | E5 + E6(仅 write_memory) + E10(审计) |
| **S3 工作推进** | WorkItem CRUD + Work 页面 + 与 execution 弱关联 | E8 + E9 接口预留 |

## 3. 目标架构：领域纯净 + 用户视角统一

```
事实源（领域纯净，各自独立）
  work_items           ← 对外承诺，用户唯一认的「事」
  collaboration_requests / decision_records   ← 协作与决策
  agent_executions / attempts / events        ← 执行事实
  memory_proposals / memory_items             ← 知识
         │
         ▼  只读投影（不做双写，不建新表）
  Work Thread Projection
    以 work_item_id 聚合，按时间排序
    { kind: MESSAGE | DECISION | EXECUTION | MEMORY, ref, summary, state }
         │
         ▼  UI 只消费投影
  Inbox（跨项目） / Channel（就地） / Work 页（单件事）
```

关键约束：投影层**不落库**（或只做缓存），避免制造第 7 个事实源。

## 4. UX 问题与建议

### U1（最重要）缺全局 Inbox —— 人类是拉模型，消息流是推模型

人类一天来几次，需要"有什么事等我"；Channel 消息流是持续推送的。现在审批记忆、补上下文、看决策**散落在消息流里**，P6 审批中心设计了但没做。

P4「待审批 3」/ P5「待办 2」/ P5b「needsN 2」三个数字互相打架，根因就是**没有统一的 NeedsYou 聚合契约**。

**建议**：
1. **Inbox 作为产品第一入口**（不是 Channel），跨项目聚合 5 类：待审记忆 / 待补上下文 / 待决策 / Agent 报错 / 超时未决。顶栏 badge。
2. Channel 内的卡片降级为**就地镜像**，操作后同步状态、从 Inbox 移除。
3. 04 文档已经定义了 `notifications.category='NEEDS_HUMAN'` + `urgency`——把它提升为 MVP 第一优先级页面，而不是 Delivery 的附属品。

### U2 状态表达过载：6 色相 + 3 lifecycle = 用户看不懂

现在只靠 7px 圆点 + 颜色区分 6 态，THINKING 与 WORKING 只差"有没有呼吸动画"。

**建议**：
1. **颜色只分 3 组**，不靠色相区分语义：
   - 需要人类行动（琥珀 / 红）
   - 系统在跑（绿 / 蓝 / 紫）
   - 不可用（灰）
2. **双编码**：颜色 + 图标或文字，满足无障碍。现在 P5b 白字 on `#EF9F27` 对比度约 2.1:1，不达 AA。
3. **lifecycle 用文字徽标**（已暂停 / 已禁用），圆点只表达 activity。DS §4 已经这么写了，但四个原型零落地。
4. P5 右栏常驻 7 行"6 态图例"改成 hover popover。

### U3 Agent 输出会冲垮时间线

P5 源码注释自己承认"为展示而平铺"；P5b 的 `xcard` 完成后 `<pre>` 仍全展开。

**建议**：
1. Agent 长输出**默认折叠为摘要卡**（结论 1–3 行 + 耗时 + token + 产物数），点击展开。
2. 流式输出放**抽屉/侧栏**，主时间线只留一条锚点消息「XX 完成分析（3 个产物）」。
3. 提供过滤：只看人类 / 只看决策 / 只看我的 @。

### U4 缺"AI 团队态势"主画面

用户最强的问题不是"这个项目怎样"，而是"**我的 AI 团队现在怎样**"——谁在跑、谁卡住、谁花钱多了、谁报错。

**建议**：做一个 Fleet / 团队态势页作为默认首页：Agent 卡片墙 + activity + 当前任务 + 今日成本 + 异常高亮。这是 MateOS 区别于 Slack 的核心画面，不该是 P4 的副产品。

### U5 成本闸门不可见

`daily_limit_usd` / `monthly_budget_usd` 有 DB 字段、P3 有 `$12.40`，但**没有预警 UI 和紧急停机入口**。人类闸门缺了一块。

**建议**：Agent 卡片 + 顶栏显示预算进度条；80% 告警；触顶自动 `lifecycle=PAUSED` 并通知 owner；顶栏一键"全部暂停"。

### U6 原型与设计系统的落地债

| 问题 | 位置 | 建议 |
| --- | --- | --- |
| tokens 缺 spacing scale / 字号阶梯 / z-index / 动效时长 | `tokens.css` | 补 4px 基准 spacing + 5 级字号，否则组件间距各自为政（P3/P4 已硬编码 12px） |
| 无暗色模式，硬编码 `#fff` 约 18 处 | 全部原型 | 现在补 `[data-theme]` 成本最低，等组件多了再补要重做 |
| 并发 execution 渲染 bug：只取第一个 `#xbody` | `P5b` L557 | 组件以 `execution_id` 为 key，不用全局 id 选择器 |
| 零 aria / 零 media query | P3/P4/P5/P5b | P5b 固定 60+306+296，1366 宽下 main 只剩 ~700px；至少定 3 个断点，右栏 <1280 折抽屉 |
| 交互全死链，`goto()` 是空占位 | 全部原型 | 至少做到路由级可点，否则评审无法验证流程闭环 |
| 驳回无理由输入，但 E5 要求 `reject_reason` 必填 | `P5` L584 / `P5b` L602 | 补驳回理由弹窗 |
| 硬编码数据（P5 `approveMem()` 写死 channel） | `P5` | 改数据驱动，否则换频道就点错 |
| Topic 5 态含 `review`，与 04 文档冲突 | `P5b` | 按文档改原型 |

## 6. PRD §11 开放问题的建议

| 开放问题 | 建议 |
| --- | --- |
| 产品名称 | **MateOS** 保留。"OS"这个隐喻正好对应你要做的定位（Agent 是成员不是工具），改名成本大于收益 |
| WorkItem 是否要 EPIC/STORY/TASK/BUG 四级 | **MVP 只留 TASK + BUG**。EPIC 层级感是 Jira 用户的习惯，不是 MVP 需要验证的假设；加回来只要改一个 CHECK 约束 |
| Built-in 是否要 Sprint/Backlog | **不要**。扁平列表 + 状态过滤足够验证"人和 Agent 一起推进工作"；Sprint 是 Jira 迁移负担不是价值 |
| Jira OAuth 授权粒度 | **Org 级**。你已经把 Connection 改成 `(org_id, owner_user_id)` 了，UI 跟着走；项目级会导致同一 Jira 实例重复授权 |
| AgentCard lifecycle × activity UI 组合 | 圆点=activity（3 组色），文字徽标=lifecycle（非 ACTIVE 才显示），hover 出原因。别试图用颜色表达 18 种组合 |
