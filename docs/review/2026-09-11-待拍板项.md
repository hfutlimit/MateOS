## P1 · Connector envelope 是否加 `v` 版本字段

| 项 | 内容 |
| --- | --- |
| 现状 | `SYSTEM_DESIGN` §6.5 写 envelope 带 `"v": 1`；`detailed/03` §2 与实现（`MateOS.Contracts.Protocol.Envelope`、`WsEnvelope.Validate`）**都不带** |
| 影响面 | 若加：所有帧（含 E3 channel 域的 `message.created` / `resume.ack`）都要带 `v`，`WsEnvelope.Validate` 需改，已上线的 WS 客户端需同步 |
| 不加的代价 | 未来做不兼容协议升级时，没有逐帧版本位，只能靠「先发 hello 声明版本」或双端点 |
| 当前取值 | **不加**（按实现与 `detailed/03`） |
| 需要的裁决 | 是否现在就为未来升级留位 |

## P2 · REST 是否加 `/api/v1` 前缀

| 项 | 内容 |
| --- | --- |
| 现状 | `SYSTEM_DESIGN` §8 写 `Client ↔ API = REST /api/v1 + JWT`；实现**没有**前缀（端点是 `/auth/*`、`/channels/*`、`/work-items/*`…） |
| 影响面 | 若加：所有端点映射、集成测试路径、未来的前端调用与 `contracts/openapi` 全要带前缀 |
| 不加的代价 | 未来 REST 不兼容变更只能靠新增路径（如 `/v2/...`）而非前缀切换 |
| 当前取值 | **不加**（按实现） |
| 需要的裁决 | 是否在写 `contracts/openapi` **之前**加前缀——一旦 OpenAPI 与前端按无前缀生成，再改成本会明显上升 |

> 顺序提醒：这项与 P3 有依赖。先定 P2，再定 P3，最后才写 `contracts/openapi`。

## P3 · OpenAPI 契约的产出方式

| 项 | 内容 |
| --- | --- |
| 选项 A | **运行时生成**（`Microsoft.AspNetCore.OpenApi` 的 `AddOpenApi` / `MapOpenApi`）：与实现零漂移，但产物需要跑起宿主才能拿到（当前宿主启动依赖 PG），且生成内容不易人工评审 |
| 选项 B | **手写 OpenAPI**：可评审、可离线用，但会引入**第三份表述**，必然漂移（本次 `contracts/` 落地已经证明「散文表述会漂移」） |
| 选项 C | 手写为源、生成 C# / TS（`detailed/09` §4 的原意）：方向最正，但需要 codegen 工具链，工作量最大 |
| 当前取值 | **未定**——`contracts/openapi/` 刻意留空 |
| 需要的裁决 | 选 A / B / C。在裁决前不要手写一份大而全的 OpenAPI |
